# Task —— 数据世界的出题编译器

**中文** | [English](README.md)

`data_world` 把因果 DAG 编译成数据世界；`task` 把数据世界编译成**带评分细则的分析题**。

它与 `dag_factory` 互为镜像：`dag_factory` 是**独立前置工具**，只靠 `dag.json` 与主
流程相连；`task` 是**独立后置工具**，只靠 `<world>/` 与主流程相连。两者都不进入
`data_world` 的生成管线，都单向复用 `data_world` 的模块（`dag` / `fs` / `sdk` /
`envfile`），反向没有任何依赖。

```
dag_factory ──dag.json──▶ data_world ──<world>/──▶ task ──tasks.json──▶ harbor
```

## 用法

```bash
# 出题：世界 → tasks.json（世界目录只读，绝不被改写）
python -m task synth --worlds ./outputs/worlds --out ./tasks -v

# 导出：tasks.json → harbor 基准任务目录（判分在容器内进行）
python -m task export --tasks ./tasks --out ./benchmark
```

本包有两个阶段：`synth` 出题、`export` 导出 Harbor 基准任务（容器内判分的
实现随导出 ship 进任务目录）。产物 `tasks.json` 同样可交下游评测工具消费。
`synth` 可断点续跑：按 `tasks.json` 里已有的 task_id 跳过（采样是
确定性的，重跑落到同一批目标）；`--force` 忽略已有产物全部重出；`--task-id`
只出指定题（可重复）。

共享机器上应通过环境变量（项目根 `.env` 的 `ANTHROPIC_*`）或运行平台的密钥机制
注入凭据；命令行 key 参数会进入 shell 历史，不应写进脚本。

## 出题的第一性原理

数据分析里**没有**检索式「多跳问答」那种题。给定一个 DAG 上的目标节点，能问的
只有两件事：

- 沿**入度**看「原因」——哪些因素驱动或预示它的变化；
- 沿**出度**看「后果」——它的变化关联到哪些下游结果。

于是采样只有一个维度：按**拓扑深度**分 K=4 层，每层各取该方向度数
Top-1 的节点，每世界最多 2K=8 道题。分层是为了避免全局 Top-K 退化成 hub 偏好；
同度数按 `dag.json` 的节点顺序定序，保证重复采样落到同一批目标（续跑的前提）。

出题 agent 的探索过程**完全不受限制**：不给流程、不给文件清单、不给统计方法建议。
它必须先知道数据实际长什么样（含瑕疵）才能写出可核验的 evidence；预设流程只会让
它照抄流程而不去核验数据。硬约束只有三条：交付格式、「不得泄漏结论」、**题面不得
出现编号清单**。

第三条不是排版偏好，而是**出题提示词的结构会被当成题面的范本**。早先 `[题面原则]`
本身是一个 1.–5. 的编号列表，实测 36 道题里 **26 道（72%）** 的题面照抄出一个编号
清单，且 **26/26** 的条目都是提示词措辞的回流（`混淆`/`伪线索`/`join 键`/`口径`/
`粒度`/`方向`/`量级`/`异质性`/`局限`/`可行动`）——连 `[工作方式]` 的「不要带着预设
流程去套」和 rubric 两节的维度描述都被搬进题面。其中 **42 处**点名了 rubric 里的
具体字段标识符（`p000002/cause_3` 一道 9 个：`event_type`/`issuing_body`/
`latency_days`/…），等于把解题大纲连同该查哪些字段一起送给答题者，而同一份提示词
的 `[题面原则] 1.` 恰恰要求「不是步骤教程」——提示词自我违背。危害有三：题面替
答题者列好了报告骨架，考不到「自己判断该看什么」；`insight_discovery` 的分因此更
易拿，带编号的 26 道与不带的 10 道**不在同一难度尺度**，混在一个 benchmark 里平均
无意义；`check_no_leak` 只断言题面不含 rubric **原文**，挡不住这种「换句话说点名
同一批字段」的泄漏。

根因是**两类受众混写在同一段文字里**：给出题者的指令与给答题者的题面内容不分，
出题者分不开就把结构和词表一起搬过去。因此提示词按受众切分小节（`[题面
（task_prompt）怎么写]` / `[rubric 怎么写]`）、全部改用无编号段落、显式禁止题面
出现编号清单，并在 rubric 维度描述后声明「这些维度词不要搬进题面」。rubric 两节
也一律直呼真键名 `data_computation` / `insight_discovery`：早先用 `A.`/`B.` 排版
标号，正文却写成「rubric 只有 A、B 两个键」，而 JSON 里并没有叫 `A` 的键。

**题面的标准是业务日常那种短平快但明确的分析委托。** 二三百字、一到两段，说清身份与
要回答的业务问题。这一条标准同时解释了长度和内容，所以它取代了「不许泄漏细节」式的
罗列：真实委托方只知道自己想弄清什么，不知道数据里有什么坑——那正是他请分析师的原因，
因此他说不出「注意口径会影响结论」「这两个文件靠 `customer_id` 关联」；而出题者刚把
世界摸透，这些话张口就来。正面给标准而非反面列禁令，模型才知道该怎么落笔。

题面越长越必然滑向转述数据清单、瑕疵种类、关联键或「注意某处会影响结论」，而这类泄漏
是**转述而非照抄**，`check_no_leak` 结构上抓不到（它比对 rubric 原文），只能靠提示词
约束。「明确」必须与「列条目」分开说明，否则会被混为一谈：明确指问题本身有边界（回答
哪件事、关于谁、什么口径的业务结果），而把交付内容列成清单是把报告骨架递过去。

**不给待填项。** 早先要求题面「交代身份情境、手上有哪些数据、要回答什么、要交付什么」
——一份**内容清单**与一份编号清单是同一种东西，出题者逐项照办，实测产出 641 字并预告
了瑕疵种类与关联键。同理不再逐条点「不列数据清单 / 不预告瑕疵 / 不点名关联键 /
不提示陷阱」：这些都是同一机制的实例，给出标准与一个反例即可泛化，而并列的禁令清单
本身也在示范清单体。

**数据目录不写进题面。** 数据位置由发题侧按规则补上（约定数据在 `env/` 下），题面
再说一遍纯属重复，且一提目录就容易顺手描述目录内容。

**资料必须带绝对路径指名。** 副本由 `--add-dir` 挂进会话，而 agent 的 cwd 是副本
之外的空 `run_dir`——提示词写裸文件名（"可自由审计 WORLD.md、dag.json、.build/"）
时，这些名字在 cwd 下并不存在。实测 36 道题的 rubric evidence 里引用 `WORLD.md` 的
**为 0**、引用 `.build/` 的仅 **4** 道，agent 基本只靠 `Glob` 摸到了 `env/`：世界
说明书与 canonical truth 这两份最该用来核验 evidence 的资料，事实上从未被打开。
`build_synth_prompt` 因此**必传** `world_copy` / `run_dir` 绝对路径（不给缺省值——
静默退化成裸文件名正是这个 bug 本身），并显式要求先读 `WORLD.md` 建立全局认识。

## rubric：两个部分

分节界线是**解题阶段**——分析之前 / 分析之中：

| section | 前缀 | 判什么 |
|---|---|---|
| `data_computation` | `dc-N` | 把原始文件变成一张能分析的表这一路上的每一步：文件与字段、记录粒度、关联键、日期与编码解析、缺失与重复处理、该剔除或修正的行、去重排序后的行数、分母口径。**重点是预处理与清洗** |
| `insight_discovery` | `id-N` | 拿到干净表之后做的所有事，**含其中的计算**：分组比较、相关与滞后、去趋势、控制混杂、排序与异质性、量级、反证/伪线索、机制边界与局限 |

判据只有一句：这个数字是在**整理数据**时得到的，还是在**回答问题**时得到的。不按
"简单还是深刻"切——那样描述时两节词表会重叠（`关键数值` 与 `方向与量级` 划不开一个
相关系数），结果清洗步骤被挤掉，而分析产出的统计量因"算起来很技术"被归进
`data_computation`。相关系数、回归斜率、分位差、滞后期数一律属 `insight_discovery`。

每条评分点只有 `criterion` + `points` 两个字段（`contract.ITEM_FIELDS`），校验器拒掉
多余字段。原先另有 `evidence` 存"裁判专用金标准"，与 `criterion` 边界天然模糊——两者
都在描述同一个事实，可核验数值写哪边全凭出题者猜，而判分拿到的是拼接后的文本，
拆两个字段并没给它额外信息。合并后规则唯一：`criterion` 自包含到能独立判定。

分值：普通事实 1–3 分，关键事实最多 5 分；**负分项** −1..−3。

**正分点必须同时"必要"且"确定"。** 两关拦的是两种不同的坏评分点，缺一不可。

*确定*管「这个事实可不可靠」：出题者实际用几种合法口径都算过，任何一条路都得到同一
结论，因此判分可以只看结果不看路径。一个量取决于走哪条路（分母取人数还是人月、
含不含未激活期、异常值是否截尾）时，不奖励其中任何一个具体值，而是把已知会走偏的那条
路写成负分项——不确定的量仍然能确定地判定它的边界。这个判断只有跑过数的出题者才知道，
无法模板化，所以提示词给的是理由而非规则表。

*必要*管「这个事实该不该考」：正分点要么是通往答案绕不过去的一步，要么是答案里必须
出现的结论。判据是一个反问——把它从答卷里去掉，答卷还完整吗？因为 reward 的分母是
正分总和，这一关直接决定 reward 的标定：每多一条题面没问的正分点，都在压低一份
本该满分的答卷的上限。出题者摸透世界后必然撞见大量真实但题面没问的旁支发现（实测一条
「运动项目结构由俱乐部供给决定」占 2/36 分，而题面只问了注册倾向、参与深度、留存三
件事），它们完全确定，所以只靠确定性关卡拦不住。判据必须落在题面上，而非出题者的兴趣。

必要**不等于**「在报告里留得下痕迹」：按主键去重、带前导零的编码按字符串读，做对了无痕、
做错了下游全错，属绕不过去的一步，仍是正分；对应的负分写的是走错会得到哪个具体错数，
两者不重复。提示词显式写明这点，否则「过程细节」会被整批降级成负分，而
`data_computation` 正是以过程为主的那一节，降完就只剩负分了。

出题侧与判分侧必须对偶：若允许口径依赖的数值当正分点，判分那条「数值应与
criterion 一致」就会把走另一条同样正确路径的答题者判错。判分只看结果不看路径，
前提正是这里的正分点路径无关——改一侧必须同时改另一侧。

**两节合计至少一条正分**，由 `validate_task` 硬校验。reward 的分母是两节合计的
正分总和，全为负分时分母为 0、reward 对任何作答恒等于 0——校验通过而判分静默失效。
只约束全局、不要求每节都有正分：确定性事实集中在哪一节是这个世界数据的性质，逼一个
口径分歧极大的 `data_computation` 硬凑正分点，正是这条规则要避免的事。

**负分项不单独成节**，按判的是数据操作还是洞察归入上面两节之一，只靠 points 为负
区分。这一点必须由 schema 示例 + 校验器共同保证，光靠提示词说不住：早先提示词写
「另外请务必再写 2-4 条负分项」而 schema 只给两个正分示例，模型普遍读成「另开一节」
——实测 35 道题里 24 道自创了 `negative` / `negative_scoring` / `negative_rubric` /
`negative_items` 四种节名共 117 条负分项，而 `build_rubric` 只遍历 `SECTIONS`，
这些条目**校验通过、判分时消失**（占全部负分项的 87%）。现在 `validate_task` 遇到
未知 section 直接报错回喂重试。

判分口径（产物契约，下游判分实现应遵循同一口径）：

- 正分项 `status=satisfied` 得分；
- 负分项 `status=triggered` 才扣分（报告没提到不算触发）；
- `reward = clamp(总分, 0, 正分上限) / 正分上限`，恒落在 [0,1]：触发负分项最多压到 0，不出现负 reward。

`dc-N`/`id-N` 编号由 `contract.build_rubric` 生成，是判分结果与评分点的关联键，
**改动即破坏历史数据可比性**。

## 不变量

0. **`env/` 的位置由一处解析。** `contract.resolve_env_dir` 先找出题留下的
   `<tasks>/<world>/world_copy/env`，没有则回落 `--world-root` 指的
   `<world_root>/<world>/env`；`WORLD_COPY` 常量也定义在 `contract`，出题（写副本）
   与导出（取 `env/`）同源。大规模出题一般用 `--no-keep-copy` 不留副本
   （副本随世界数量线性占盘），产物里没有 `world_copy`，此时 `export`
   必须传 `--world-root` 回落到世界目录——副本本来就是原始世界的逐字节拷贝，
   `env/` 内容相同。
1. **世界目录只读，且是结构保证。** 出题拷一份副本后 `chmod` 去掉写位，agent 的
   工作目录在副本之外——写世界直接 `EACCES`。不靠 sha256 清单事后检测污染再重拷：
   检测只能发现已经发生的事，结构能让它不发生。（权限位对 root 无效；出题按设计
   以普通用户跑。）
2. **评分语义只有一个实现。** 判分由 `export/grade.py` 拥有；harbor 容器 verifier
   用的是导出时逐字节拷进 `tests/` 的同一份源码，判分提示词由 `prompts.py` 的
   `JUDGE_PROMPT` 定义一次、导出时生成自包含的 `judge_prompt.py`。不允许"包内一份、
   容器一份"各自演化。
3. **契约由一处拥有。** `contract.py` 同时被 prompts（声明交给 agent 的 schema 与
   交付方式）、pipeline（校验产物）与导出（`build_rubric` 打平、`check_no_leak`
   防泄漏）使用，不存在"prompt 要求写文件、验证器只认标记块"这类漂移。
4. **凭据只从环境变量读。** 代码里不落任何 token；本机走项目根 `.env`。
   harbor 的评测平台没有运行期环境变量注入通道，judge 凭据在导出时写进每个任务的
   `tests/judge.env`（任务目录落盘即 0700），解析顺序与容器内 `judge.py` 一致
   （`JUDGE_*` 优先，回落 `ANTHROPIC_*`）。
5. **LLM 调用一律流式。** 出题会话走 `--output-format stream-json`，judge 走 SSE。
   超时语义因此是**事件之间的空档**而非整段生成时长：模型还在吐字就不算超时。
   出题提示词于是不需要任何"限制输出长度"的自我约束——rubric 该写多少条写多少条。
6. **防泄漏是两条独立通路各堵一次。** 题面侧 `contract.check_no_leak` 断言不含
   rubric 的结论性文本；镜像侧白名单只 `COPY data/`，并在构建期断言 `WORLD.md` /
   `dag.json` / `.build` 不存在。

   题面侧的判据是「片段既是题面子串、又含**结论标志**（数字、量级词、因果或比较词）」，
   而非原先的「剥掉标识符后剩余自然语言够长」。长度判据在两个方向都失效：旧正则
   `[\w./{}(),：-]+` 的 `\w` 在 unicode 下**包含汉字**，"留存呈饱和曲线，12 个月后边际
   增益趋近 0"被剥成 `，`（4 字符）而落到 8 字符阈值下豁免——中文结论句照抄进题面一律
   不报；改成只剥 ASCII 后，`env/a.csv 与 env/b.csv 按 uid 关联` 剩下"与按关联"够长，
   题面合法点名文件反而误报。区分两者的不是长度而是"有没有在说结果是多少"。数字必须
   在**未剥离**的原文上测（`7500 行`、`高 3.2 个百分点` 里的数字是最强信号），路径里
   紧挨字母的数字（`queue_metrics_5m.parquet`）则随标识符一起剥掉。合并 `evidence`
   后 `criterion` 同时承载口径与结论，这条是唯一的兜底。词表必然不全，主防线仍是出题
   提示词那条硬底线。
7. **重试分层。** `runner` 负责瞬时传输错误（`_TRANSIENT_RE`，默认重试 10 次，
   20 秒起指数退避、单次最多 600 秒）；`pipeline` 负责产物非法，且把校验错误文本
   回喂给下一次 prompt。两者不互相代偿。
8. **身份字段单向注入，不经 agent 往返。** agent 只交 `task_prompt` + `rubric`
   （`contract.AGENT_FIELDS`）；`task_id` / `task_kind` / `target_node` /
   `degree_kind` / `degree` 由 `contract.attach_identity` 从 `select_targets` 的指派
   直接写入（`contract.IDENTITY_FIELDS`）。这些是**我们自己的簿记**：`task_id` 决定
   目录名、`tasks.json` 的键与续跑判定，agent 抄的那份早先只被拿去和指派比对一次就
   丢弃。让它抄一遍已知常量，只会凭空多出一类「抄错就整份重试」的失败可能（实测 36
   道题 0 处抄错，即这条校验从未抓到东西）。注入后 `tasks.json` 的字段集与旧产物
   **完全相同**，只是填法从「校验」变成「注入」，故与历史产物向后兼容。

## 目录结构

```
task/
  contract.py   产物契约：schema、交付标记、校验、rubric 打平、泄漏检查
  runner.py     流式 agent 运行器（ClaudeRunner 的流式替代）
  cli.py        子命令 + 错误边界
  synth/        出题
    sampler.py    分层选目标节点（复用 data_world.dag 的校验与归一化）
    prompts.py    出题提示词
    pipeline.py   编排：只读副本、校验重试、续跑、聚合
  export/       Harbor 导出
    harbor.py     导出器：tasks.json → harbor 任务目录
    grade.py      判分唯一实现 + 容器 verifier 入口
    judge.py      judge 客户端（流式 SSE、零第三方依赖）
    prompts.py    JUDGE_PROMPT（导出时生成自包含 judge_prompt.py）
```

`contract.py` 与 `runner.py` 留在包根：前者是产物契约的唯一定义处（prompts 声明、
pipeline 校验、导出按同一口径消费），后者被出题会话与 CLI 共用。

`export/` 里的 `grade.py` / `judge.py` / `prompts.py` 是随容器 ship 的判分资产：
导出时逐字节拷进任务目录的 `tests/`（`judge_prompt.py` 由 `JUDGE_PROMPT` 生成），
容器 reward 必须来自这份源码本身才可比较——这是不变量 2 的落地方式。

| 模块 | 是否调进程/网络 |
|---|---|
| `contract` / `synth.sampler` / `synth.prompts` / `export.prompts` / `export.harbor` | 否 |
| `export.grade` | 否（judge 由调用方注入） |
| `export.judge` / `runner` | 是 |
| `synth.pipeline` | 是（只经注入的 runner） |
